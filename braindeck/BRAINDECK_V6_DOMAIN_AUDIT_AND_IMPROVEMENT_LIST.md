## Part 1. 6대 영역별 현 기준(As-Is) 정밀 분석 및 문제점 진단

### 1.1 [영역 1] 데이터베이스 & 스토리지 아키텍처 (DB & Persistence)

#### 📌 현 기준 (As-Is)
1. **Python 백엔드 (`adapters/sqlite_store.py`)**:
   - SQLite WAL 모드 + `BEGIN IMMEDIATE` 단일 작성자 트랜잭션 적용.
   - 총 11개 테이블(`decks`, `notes`, `cards`, `revlog`, `review_undo_journal`, `review_events`, `note_facets`, `confusion_edges`, `confusion_matrix_weights`, `exam_plans`, `media_cas`) 운영.
   - `ALTER TABLE` 마이그레이션을 통해 `cards`에 `flag`, `buried_today`, `buried_until_date`가 추가되어 있고 `decks`에 `target_days`, `daily_new_limit`, `daily_review_limit`, `plan_applied`가 존재함.
2. **Android 네이티브 (`StudioDatabase.kt`)**:
   - Room SQLite DB 4개 엔티티(`DeckEntity`, `NoteEntity`, `CardEntity`, `RevlogEntity`) 운영.
   - `CardEntity`는 `state`(`new`/`learning`/`review`)와 `queue`(`0:NEW`, `1:INTRADAY`, `2:REVIEW`, `-1:SUSPENDED`, `-2:USER_BURIED`, `-3:SIBLING_BURIED`)를 정수형으로 깔끔하게 분리하고 `RevlogEntity`도 비연쇄(Non-cascading)로 설계됨.
3. **Apple PWA 오프라인 금고 (`BrainDeckLocalVault` in `viewmodel.js`)**:
   - 브라우저 `localStorage`의 단일 키에 덱·카드·리뷰 이력 전체를 `JSON.stringify()`로 직렬화하여 저장.

#### 🚨 구조적 문제점 및 한계
1. **[치명적 P0] PWA `localStorage`의 `Fail-Open` 조용한 데이터 유실 (`viewmodel.js:2108-2114`)**:
   - `saveDb()` 함수가 `localStorage.setItem` 호출 시 발생하는 `QuotaExceededError`(5MB 한도 초과)를 `catch (_e) { // ignore quota error }`로 삼켜버립니다.
   - 1,000장짜리 덱 여러 개와 학습 이력이 쌓여 5MB를 넘는 순간부터 **화면상으로는 학습과 채점이 정상 진행되는 것처럼 보이지만 디스크에는 전혀 저장되지 않으며, 새로고침 한 번에 모든 진척률이 날아갑니다.**
   - 또한 매 카드 채점 시마다 수 메가바이트의 JSON 전체를 메인 스레드에서 동기 직렬화하므로 모바일에서 버튼 응답 지연(Frame Drop)을 유발합니다.
2. **[치명적 P0] Python `cards.state = 'suspended'` 덮어쓰기 결함 (`sqlite_store.py:688`)**:
   - Android는 `queue = -1`로 일시정지를 표현해 원래 학습 상태(`learning`/`review`)를 보존하지만, Python 백엔드는 `UPDATE cards SET state = 'suspended'`로 `state` 컬럼 자체를 덮어씁니다.
   - 그 결과 일시정지(Suspend)를 해제할 때 이 카드가 원래 새 카드(`new`)였는지, 장기 복습(`review`) 카드였는지 복원할 근거가 사라집니다.
3. **[P0] Python `revlog` 2단 연쇄 삭제 (`ON DELETE CASCADE`)**:
   - `notes → cards → revlog`에 모두 `ON DELETE CASCADE`가 걸려 있어, 사용자가 오타 수정이나 정리를 위해 노트/카드를 삭제하면 그동안 쌓인 귀중한 FSRS 복습 이력(`revlog`)까지 영구 삭제됩니다.
4. **[P0] Android `DeckEntity`의 D-Day 학습 계획 컬럼 누락 및 스키마 비대칭**:
   - Python `decks` 테이블에 있는 `target_days`, `daily_new_limit`, `daily_review_limit`, `plan_applied`가 Android `DeckEntity`에는 빠져 있어, D-Day 학습 계획의 영속성과 백업/복원 정합성이 깨져 있습니다.
5. **[P1] 시각 표현 불일치 (`due_at TEXT` vs `dueEpochSec INTEGER`)**:
   - Python은 ISO-8601 문자열(`due_at TEXT`) 비교를 수행하고 Android는 `dueEpochSec`(`Long`)을 사용하여 타임존 변경이나 단기(1분/10분) 스텝 계산 시 정밀도 차이가 발생합니다.

### 1.2 [영역 2] 작동 방향 & 코어 스케줄링/큐 메커니즘 (Core Engine & Operational Flow)

#### 📌 현 기준 (As-Is)
1. **FSRS-5 기억 모델 (`domain/fsrs_math.py`)**:
   - 난이도($D$), 기억 안정성($S$), 인출 확률($R$) 3변수 기반 상태 전이 및 4단계 평가(`다시 1` / `어려움 2` / `알맞음 3` / `쉬움 4`) 구현 완료.
2. **D-Day 학습 플래너 & 일일 할당량 슬라이서**:
   - 목표 기간(`D-7 ~ D-90`)과 가용 시간(`15~60분`)에 맞춰 일일 신규 카드 할당량(`daily_new_limit`)을 산출하고 큐를 슬라이싱함.
3. **적응형 인출 진화 (`Adaptive Solve Mode`)**:
   - 새 카드는 `4지선다(Recognition)` ➔ 복습 카드는 `직접 타이핑(Recall)`으로 진화하며, 초·중고·성인 연령별 프리셋 지원.

#### 🚨 구조적 문제점 및 한계
1. **[P0] 단기 학습 스텝(`1분 / 10분` Intraday Learning Queue)의 부재**:
   - A-SRS 학습의 핵심은 처음 본 카드나 틀린 카드를 **같은 세션 안(1분 뒤, 10분 뒤)** 에 다시 물어봐서 단기 기억을 고정한 뒤 졸업(Graduate)시키는 것입니다.
   - 현재는 일 단위(`due_days`) 중심으로만 큐가 돌아가서, 방금 틀린 카드가 바로 다음 장에 곧바로 튀어나와 단기 잔상만으로 맞히게 되거나(간섭 효과), 반대로 내일 이후 장기 간격으로 바로 넘어가 기억 안정성($S$)이 왜곡됩니다.
2. **[P0] Python · Web JS · Android Kotlin 3중 로직 복제로 인한 드리프트**:
   - 스케줄링, 형제 카드 숨김(Sibling Burying), D-Day 일일 할당량 계산, 진척률 산출 로직이 3개 언어에 각각 수작업으로 복제되어 있습니다.
   - 최근 발생했던 **"4장만 나오고 끝나는 버그(`concept:` modulo-4 충돌)"** 와 **"30장 vs 43장 카운트 불일치"** 모두 3원 복제 구조에서 기인한 전형적인 드리프트 현상입니다.
3. **[P1] FSRS-5 19개 가중치(`w[0..18]`) 고정 상수 한계**:
   - 모든 사용자와 모든 과목(영단어 vs 한국사 연표 vs 이공계 공식)에 동일한 기본 가중치 상수(`DEFAULT_FSRS5_WEIGHTS`)만 적용되고 있으며, 누적된 `revlog`를 바탕으로 개인의 실제 망각 속도에 맞춰 가중치를 튜닝하는 최적화기가 없습니다.
4. **[P1] 도메인 계층의 UI 문자열/이모티콘 오염 (`domain/pack_store.py:506`)**:
   - 순수 비즈니스 규칙만 담아야 할 도메인 계층이 `"✅ 앱 내 장착 완료"`, `"🔒 스토어 구매 (₩1,500)"` 같은 이모티콘 포함 화면 문구를 직접 조립해 반환하고 있습니다.

## Part 2. "이모티콘 1,127곳 퇴출" 및 프로페셔널 디자인 시스템 개편 규격 (De-Emojification Standard)

> **사용자 핵심 피드백**: *"이모티콘이 많아져서 유치해진다!"*

### 5.2 설계 시 기준을 명확히 잡지 못했던 5대 핵심 작동 기준의 디테일 정본 명세 (`S1 ~ S5`)

최초 설계 당시 *"FSRS를 쓰고 D-Day 플래너와 진척률을 보여준다"* 는 큰 방향만 있었을 뿐, 아래 5가지 세부 엔지니어링 수식과 상태 전이 규칙이 정본(Canonical Spec)으로 못 박혀 있지 않아 Python·Web·Android가 각자 다르게 구현하면서 오류가 발생했습니다. 이를 **`BrainDeck Operational Standard v7.0`** 으로 명확히 확정합니다.

#### 📐 [기준 S1] 인트라데이(Intraday) 스케줄러 & 20분 선행 학습 창(`Learn-Ahead`) 정본 명세
1. **5대 카드 상태(`state`) × 큐(`queue`) 전이 규칙**:
   - `NEW (state='new', queue=0)`: 아직 한 번도 학습하지 않은 카드.
   - `LEARNING (state='learning', queue=1)`: 첫 학습 중인 카드. 인트라데이 스텝 `[60초(1분), 600초(10분)]` 적용.
     - `Again(1)` ➔ `step=0`, `due_epoch_sec = now + 60` (1분 후)
     - `Hard(2)` ➔ 현재 `step` 유지, `due_epoch_sec = now + 300` (5분 후, **절대 1일 간격으로 점프 금지**)
     - `Good(3)` ➔ `step == 0`이면 `step = 1, due_epoch_sec = now + 600` (10분 후); `step >= 1`이면 **졸업(`state='review', queue=2, interval=1d~3d`)**
     - `Easy(4)` ➔ 즉시 졸업(`state='review', queue=2, interval=4d`) (단, `EvidenceRatingGuard` 통과 시에만 허용)
   - `REVIEW (state='review', queue=2)`: 일 단위 장기 복습 카드 (`due_epoch_sec`은 해당 복습일 로컬 04:00 KST 기준).
     - `Again(1)` 클릭 시 ➔ **`RELEARNING (state='relearning', queue=1, step=0, due_epoch_sec = now + 600)`** 으로 전이하며, 같은 날 반드시 `Good/Easy`로 다시 졸업해야 오늘의 학습이 완료됨.
2. **큐 우선순위 및 20분 선행 학습 창 (`Learn-Ahead Limit L = 1200s`)**:
   - 세션 큐 조회 시 우선순위는 **`P0 (만기 도래 인트라데이: queue=1 AND due_epoch_sec <= now)` ➔ `P1 (오늘 만기 장기 복습: queue=2 AND due_day <= today)` ➔ `P2 (신규 할당 카드: queue=0)` ➔ `P3 (선행 인트라데이: queue=1 AND now < due_epoch_sec <= now + 1200)`** 순으로 작동합니다.
   - **핵심 불변식**: `P0, P1, P2`가 모두 소진되었더라도, 방금 틀려서 `due_epoch_sec`이 `now + 10분`으로 잡힌 `P3` 카드가 존재하면 **절대 `"오늘 학습 완료"`를 선언하지 않고 즉시 `P3` 카드를 출제**합니다. (만약 `L=20분` 밖의 대기 카드가 있다면 `"완료"` 대신 `"재학습 대기 N장 (남은 시간 M분 · 지금 바로 풀기)"` 배너를 표시합니다.)

#### 📐 [기준 S2] 오늘 목표 진척률 (`today_completed / today_target`) & 전체 진도율 불변 수식
1. **하루 목표 분모 $T(d)$ 의 불변 스냅샷 고정**:
   - 학습일 $d$에 세션이 처음 열릴 때(또는 사용자가 D-Day 플랜을 변경할 때만), 오늘의 목표 고유 카드 집합 $S_{\text{target}}(d) = S_{\text{due\_review}}(d_0) \cup S_{\text{planned\_new}}(d_0)$ 및 분모 $T(d) = |S_{\text{target}}(d)|$ 를 확정하여 저장합니다.
   - 학습 도중 카드를 틀려 `Again`을 누르거나 재학습 이벤트가 발생해도 **분모 $T(d)$ 는 절대 증가하지 않습니다(`30 -> 31 -> 32` 금지).**
2. **오늘 완료 분자 $C(d)$ 의 정의 (이벤트 횟수 $\neq$ 졸업 카드 수)**:
   - 분자 $C(d)$ 는 `revlog`의 단순 클릭 횟수(`COUNT(*)`)가 아니라, **오늘 목표 집합 $S_{\text{target}}(d)$ 중 현재 시점 기준 최종 상태가 `REVIEW (queue=2)`로 졸업(Graduate) 완료된 고유 `card_id`의 개수**입니다:
     $$C(d) = \left| \{ c \in S_{\text{target}}(d) \mid \text{card}(c).\text{state} = \text{'review'} \land \text{last\_reviewed\_day}(c) = d \} \right|$$
   - 따라서 카드를 틀려 `Again`을 누르면 `state='relearning'`이 되므로 $C(d)$ 가 오르지 않고, 재도전하여 `Good/Easy`를 받아 `state='review'`로 졸업할 때 정확히 `+1` 증가합니다.
   - **일일 진척률**: $\text{today\_progress\_pct} = \min\left(100.0, \text{round}\left(\frac{C(d)}{\max(1, T(d))} \times 100, 1\right)\right)$.
   - **전체 덱 진도율**: $\text{deck\_progress\_pct} = \text{round}\left(\frac{|\{c \in \text{Deck} \mid \text{reps}(c) \ge 1\}|}{|\text{Deck}|} \times 100, 1\right)$ (한 번 이상 학습 경험한 고유 카드 비율)과 **장기 마스터율**($S \ge 21\text{일}$ 고유 카드 비율)을 명확히 구분해 표시합니다.

#### 📐 [기준 S3] 결정론적 세션 큐 상태 머신 (No Mid-Session Reshuffle)
1. **단일 카드 풀이 4단계 상태 머신**:
   - `QUESTION_PRESENTED` (문제 제시 · 채점 버튼 비활성화) ➔ `USER_ANSWERED` (4지선다 선택 / 블록 조립 / 타이핑 제출 · 정오답 및 소요시간 `duration_ms` 확정) ➔ `ANSWER_REVEALED` (정답·해설 공개 및 `EvidenceRatingGuard`가 허용한 채점 버튼만 활성화) ➔ `RATED_AND_COMMITTED` (DB 원자적 저장 후 다음 카드 전이).
2. **큐 불변성 (Queue Stability Invariant)**:
   - 세션 시작 또는 필터 변경 시에만 시드(`seed = hash(study_day, deck_id)`) 기반으로 큐를 1회 정렬/셔플합니다.
   - 카드 채점 후에는 **절대 전체 큐를 재조회하거나 재셔플하지 않습니다.**
   - `Good(3)` / `Easy(4)` 졸업 시: 현재 카드를 `activeQueue`에서 제거(Pop).
   - `Again(1)` / `Hard(2)` 재학습 시: 현재 카드를 큐에서 제거한 뒤, 단기 잔상 방지를 위해 **현재 위치로부터 최소 `k = min(4, remainingQueue.length)`장 뒤(Spacing Offset)** 에 결정론적으로 재삽입합니다.

#### 📐 [기준 S4] 학습일 경계 (`04:00 Local Rollover`) 및 시각 표준
1. 모든 타임스탬프는 DB에 **UTC Epoch Seconds(`INTEGER`)** 로 저장합니다.
2. 학습일 인덱스(`study_day_index`)는 기기의 로컬 타임존 오프셋(`tz_offset_sec`, 한국은 `+32400`)과 롤오버 시각(`rollover_hour = 4`, 즉 `14400초`)을 적용한 아래 단일 수식으로 3대 플랫폼에서 100% 동일하게 산출합니다:
   $$\text{study\_day\_index}(t) = \left\lfloor \frac{t + \text{tz\_offset\_sec}(t) - 14400}{86400} \right\rfloor$$
3. 이로써 한국 시간 새벽 3시 59분까지는 전날 학습일로 유지되고, **오전 9시(UTC 자정)에 진척률이 0%로 초기화되던 버그가 영구히 사라집니다.**

#### 📐 [기준 S5] 1,000장 코퍼스 무결성 & 덱 Upsert 멱등성 표준
1. **1,000장 코퍼스 4대 품질 게이트 (Fail-Closed)**:
   - ① **루프 패딩 금지**: 카드 앞면/뒷면에 `"· 단계 2"`, `"· 단계 3"` 등 인위적 번호 접미사를 붙여 장수를 채우는 행위를 전면 금지합니다 (`0건`).
   - ② **고유 개념 밀도 보장**: 1,000장 덱은 최소 **500~1,000개의 서로 다른 고유 원천 개념(`concept_id`)** 을 포함해야 하며, 한 개념당 파생 카드는 최대 2장(`정방향 정의` + `실제 빈칸 Cloze`)까지만 허용합니다.
   - ③ **진성 빈칸(`Cloze`) 검증**: `template_type = 'cloze'` 또는 `Lv.2 빈칸` 라벨이 붙은 모든 카드는 질문(`front`)에 반드시 실제 마스킹 토큰(`[ ___ ]` 또는 `{{c1::...}}`)을 포함해야 하며, 정답(`back`)이 질문 본문에 그대로 노출되어서는 안 됩니다.
   - ④ **4지선다 오답 풀 격리**: 오답 보기 3개는 현재 필터링된 큐가 아니라 **해당 덱 전체 노트 풀(1,000장)** 의 동일 품사/카테고리에서 추출하여, 필터 모드에서도 더미 폴백 문자열(`"소개하다"` 등)이 절대 나오지 않도록 합니다.
2. **덱 생성 멱등성 (`content_hash` Idempotent Upsert)**:
   - 모든 카드는 `content_hash = SHA256(NFC(deck_slug) + "|" + NFC(template_type) + "|" + NFC(canonical_front))`를 가지며, DB에 `UNIQUE(deck_id, content_hash)` 제약을 둡니다.
   - 동일 프리셋/컬렉션을 재설치하거나 앱을 재시작할 때는 `INSERT OR IGNORE` (또는 텍스트 메타만 `ON CONFLICT DO UPDATE`, 기존 `stability/difficulty/reps/due`는 100% 보존)로 동작하여 **덱 카드 수가 `1,000 -> 2,000 -> 3,000장`으로 불어나는 현상을 원천 차단**합니다.
